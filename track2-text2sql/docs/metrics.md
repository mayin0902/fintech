# 指标口径与复算

## 可以说什么

> 将候选/训练标签 SQL 的 PostgreSQL 执行正确率从 36.6% 提升至 97.32%。

分母始终是同一批 5,635 个多轮 turn。基线取首次完整评测的 2,061 条正确；最终 verified pool 为 5,484 条。

```text
baseline = 2061 / 5635 = 36.5749% ≈ 36.6%
final    = 5484 / 5635 = 97.3203% ≈ 97.32%
absolute gain = 60.7454 percentage points
remaining failures = 5635 - 5484 = 151
```

聚合机器可读数据在 `results/summary.json`。

## 不应该说什么

- “最终模型测试准确率达到 97.32%”；
- “GRPO 把模型从 36.6% 训练到 97.32%”；
- “线上系统知道 SQL 是否回答正确”。

原因：97.32% 是经过强模型候选、评测口径修正、规则/模型修复与真库复验后的**训练标签/候选集质量**。它证明的是数据与 Agent 反馈 pipeline，而不是独立测试集上的模型泛化成绩。

## 为什么有 36.6% 与 37.2% 两个基线记录

项目留档中另一次基础模型复跑为 `2095/5635 = 37.18%`。两次运行使用的生成/解析产物不同，因此不能混写。简历沿用首次完整评测 `2061/5635 = 36.57%`；公开结果保留分子分母，避免只报四舍五入百分比。

## 为什么时区能带来 345 条变化

gold 中的月度时间桶按 `Asia/Shanghai` 生成，而早期 verifier 会话使用 UTC。月初边界附近的 `TIMESTAMPTZ` 会落入不同月份，使语义正确的 SQL 被误判。固定 `+08` 后正确数从 4,901 变为 5,246；这是评测校准，不应描述为模型能力提升。

## 结果比较规则

- 列名与列序一致；
- 无显式顺序要求时按**行多重集合**比较，忽略行序但保留重复次数；
- 有顺序要求时逐行比较；
- 数值用 `Decimal` 规整，避免二进制浮点噪声；
- gold 与 candidate 在同一 PostgreSQL session 语义下执行；
- 超时、执行错误、非安全单 SELECT 均不算正确。
