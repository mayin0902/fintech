# 项目技术主线：从数据库评分器到 Agent 环境

## 1. 用户问题 → Schema 理解

多表金融数据库的第一类失败不是“不会写 SQL”，而是没有把问题中的实体、指标和约束对齐到真实表列。基础模型错误中，表/列放错、别名作用域错误、臆造字段和列歧义是高频问题。

工程上先从 PostgreSQL catalog 抽取表、列、类型和外键，再按问题做相关表列裁剪。Prompt 中保留：

- 完整限定名 `schema.table.column`；
- 主外键方向；
- 文本枚举的真实取值；
- 当前轮问题依赖的已验证历史，而不是未验证的上一轮猜测。

## 2. Schema 理解 → SQL 生成

输出协议固定为一个小写 `sql` fenced block，内部只能有一条 `SELECT` 或 `WITH`。统一协议不是审美问题：它让训练数据过滤器、执行器和 reward parser 共享同一输入契约，减少静默丢样本。

生成层需要区分两种模式：

- **离线训练/修复**：同一问题采样多条候选，探索优先；
- **在线服务**：低温生成，失败后用数据库反馈定向重写。

## 3. SQL 生成 → 数据库执行

LLM 输出永远视为不可信输入。应用层快速 guard 只是一层预检，真正边界必须同时具备：

1. 数据库最小权限账号；
2. `SET TRANSACTION READ ONLY`；
3. statement timeout；
4. 单语句限制与危险函数拒绝；
5. 网络和资源隔离；
6. 固定时区与一致的 session 设置。

只有“SQL 能运行”还不够。正确性定义为列序一致、结果行的多重集合一致；不能用普通 `set`，因为它会吞掉重复行，让缺少 `DISTINCT` 或 JOIN 行爆炸的错误漏检。存在显式排序语义时才按行序比较。

## 4. 数据库执行 → 错误反馈

反馈必须结构化，而不是把完整 gold 结果泄露给模型：

- `unsafe_sql`：非只读、多语句或危险函数；
- `execution_error`：语法、表列、类型、聚合或别名错误；
- `timeout`：笛卡尔积、低效相关子查询等；
- `column_mismatch`：投影列多选/少选/顺序错误；
- `row_count_mismatch`：过滤、JOIN 粒度、DISTINCT 错误；
- `value_mismatch`：聚合口径、日期桶、Top-N、集合差等语义错误。

离线阶段知道 `expected_output`，可以判定结果对错；线上真实问答通常没有 gold，只能利用可执行性、约束检查和业务 guard。不能把离线 verifier 的能力错误地宣传成线上 oracle。

## 5. 错误反馈 → 反思纠错

每轮把“上一条 SQL + 错误类别 + 必要但不泄露答案的差异摘要”放回上下文，请模型只修当前错误。修复结果只有重新执行并命中 gold 才进入 verified pool。

分层路由降低成本与不确定性：

1. 确定性规则：枚举映射、城市后缀、日期桶、已知错误谓词；
2. 模型重写：多表 JOIN、子查询、窗口函数、复杂多轮约束；
3. 真库复验：任何来源的候选一视同仁；
4. 未通过样本隔离：不为了“凑满数据”污染 SFT。

## 6. 反思反馈 → Reward 优化

同一执行器被复用为三个数据产品：

- `reward == 1` 的 rollout 进入 RFT / verified-only SFT；
- 同题最高分与最低分组成 DPO `(chosen, rejected)`；
- 同题的 K 个在线 rollout 直接供 GRPO 做组内相对优势估计。

exact execution match 必须是 reward 的锚。格式、可执行、列数、行数、部分行重合只用于解决早期全 0 的稀疏问题，非精确命中的 shaping reward 要设上限，避免“差不多正确”压过真正正确的 SQL。

## 7. 防止 Reward Hacking

- 删除 gold 为空、常量查询等退化样本，或降低其权重；
- 在多份数据快照上验证，减少“当前快照碰巧相同”的伪正确；
- 监控空结果率、平均返回行数、SQL 长度、超时率和重复候选率；
- 对组内 reward 全相同的 GRPO prompt 不强行产生梯度；
- 验证集只用于选型和停机，不回流训练。
