# 赛道1 H20/A800 最终实验策略

更新时间：2026-05-13

目标：在 2026-05-17 比赛截止前，把当前 MoE Block 显存优化方案迁移到 H20 或 A800 上完成官方尺度实验，优先形成可提交、可复现、低风险的最终版本。

## 当前结论

当前 `track1/official/solution.py` 的主线是纯 PyTorch 实现：

- 去掉 baseline 中按 expert 构造 one-hot mask 的高显存路径。
- shared expert 和 routed experts 均按 token chunk 计算。
- 通过环境变量控制 chunk 和 activation checkpoint。
- 保持参数名、路由定义、输出定义和梯度数学定义不变。

48GB RTX 4090 本地实测已经证明：

| 配置 | SeqLen | Peak MB | Avg ms | 结论 |
|---|---:|---:|---:|---|
| `shared=131072, expert=131072, checkpoint=0` | 8192 | 4300.63 | 72.89 | 通过 |
| `shared=131072, expert=131072, checkpoint=0` | 32768 | 9328.38 | 182.32 | 通过 |
| `shared=131072, expert=131072, checkpoint=0` | 65536 | 17416.01 | 326.61 | 通过 |
| `shared=131072, expert=131072, checkpoint=0` | 131072 | 33591.26 | 620.49 | 通过 |
| `shared=131072, expert=131072, checkpoint=1` | 196608 | 32943.38 | 1129.68 | 通过 |
| `shared=131072, expert=131072, checkpoint=1` | 262144 | 41366.63 | 1485.82 | 通过 |

因此，48GB 已足够证明算法方向；H20/A800 阶段不应重复大范围探索，而应做官方环境复现、Pareto 搜索和最终稳定性确认。

## 全网资料复核后的修正

### 1. H20 和 A800 都能做完整实验

公开资料显示：

- H20 96GB：Hopper，96GB HBM3，约 4.0TB/s 显存带宽。
- A800 80GB：Ampere，80GB HBM2e，公开数据表给出约 1935GB/s 显存带宽。

判断：

- H20 更接近官方 H20 96GB 环境，优先做最终成绩确认。
- A800 80GB 显存足够做完整实验和主要调参，但带宽可能明显低于 H20，速度结果不能直接等价于官方 H20。
- 多张 A800/H20 应用于并行 trial，不应用于多卡模型并行，因为赛题是单卡评分。

### 2. 官方环境必须回到 PyTorch 2.8.0 + CUDA 12.8

PyTorch 官方 previous versions 页面提供：

```bash
pip install torch==2.8.0 torchvision==0.23.0 torchaudio==2.8.0 \
  --index-url https://download.pytorch.org/whl/cu128
```

判断：

- `CUDA 13.0 + PyTorch 2.9.1` 可以用于早期探索，但不能作为最终结论。
- 最终提交前必须在 `Python 3.12 + torch==2.8.0+cu128` 或尽量贴近官方的容器/虚拟环境中重跑 correctness 和 benchmark。
- 不需要卸载系统 CUDA；PyTorch wheel 自带 CUDA runtime，关键是 NVIDIA driver 足够新。

### 3. checkpoint 是必要兜底，但不能默认押注

PyTorch 文档说明 activation checkpoint 是以重复计算换显存；`use_reentrant=False` 是推荐路径。当前代码已显式使用：

```python
checkpoint(..., use_reentrant=False, preserve_rng_state=False)
```

判断：

- no-checkpoint 是 128K 的速度主线。
- checkpoint 是长序列、低显存和显存分数主线。
- 因为赛题显存权重高于速度，最终不能只看最快配置；必须保留一个低显存候选。

### 4. torch.compile 只能作为可放弃加速分支

PyTorch 文档说明 `torch.compile` 支持 `default`、`reduce-overhead`、`max-autotune`、`max-autotune-no-cudagraphs`。其中 `reduce-overhead` 依赖 CUDA Graphs，可能缓存 workspace 并增加显存；`max-autotune` 编译时间更长。

当前实现中存在 `unique`、`where`、按 expert Python loop、动态 token 数等数据依赖控制流，整块 `forward` 很可能 graph break。

判断：

- 不把 `torch.compile` 作为默认提交路径。
- 只尝试 compile `_shared_chunk` 和 `_expert_chunk` 这类局部矩阵计算区域。
- 首选 `max-autotune-no-cudagraphs`，避免 CUDA Graphs 带来的额外显存。
- 若 2 小时内没有稳定收益，立即停止 compile 分支。

### 5. 自动调参应做分阶段剪枝，不做大网格或盲搜

Optuna 支持 TPE、Hyperband、SuccessiveHalving 和多 worker 并行，但距离 2026-05-17 时间太短，本题参数又是少量离散系统参数，盲目引入 Optuna 成本偏高。

更高效的策略是自定义 successive-halving：

- 第一阶段用短序列和少 measure 快速排除错误/OOM。
- 第二阶段只把幸存配置推进 128K。
- 第三阶段只对 Pareto 前几名做多次重复测量。
- 每个 trial 单独开子进程，避免 OOM 后 CUDA 上下文污染后续实验。

## 最终候选配置

### 快速候选

用于争取速度分：

```text
MOE_SHARED_CHUNK_SIZE=131072
MOE_EXPERT_CHUNK_SIZE=131072
MOE_USE_CHECKPOINT=0
```

已在 48GB 上通过 8K/32K/64K/128K，128K 峰值约 33.6GB。

### 低显存候选

用于争取显存分：

```text
MOE_SHARED_CHUNK_SIZE=8192 或 16384 或 32768
MOE_EXPERT_CHUNK_SIZE=8192 或 16384 或 32768
MOE_USE_CHECKPOINT=1
```

24GB 结果显示 `ckpt_s8192_e8192` 在 131072 上约 21.3GB 峰值，但速度明显慢。H20/A800 上需要重新测量它与快速候选在官方评分权重下的相对收益。

### 大显存长序列候选

仅当隐藏 benchmark 包含 196K/262K 时考虑：

```text
MOE_SHARED_CHUNK_SIZE=196608 或 262144
MOE_EXPERT_CHUNK_SIZE=196608 或 262144
MOE_USE_CHECKPOINT=0
```

48GB 上 full no-checkpoint 在 196608 OOM；A800/H20 可能可以容纳。该方向只做少量验证，不应影响 128K 主线。

## H20/A800 实验流程

### 阶段0：环境确认，30 分钟内完成

```bash
python - <<'PY'
import torch
print("torch", torch.__version__)
print("cuda", torch.version.cuda)
print("available", torch.cuda.is_available())
print("device", torch.cuda.get_device_name(0))
print("capability", torch.cuda.get_device_capability(0))
PY
```

必须记录：

- GPU 型号和显存。
- NVIDIA driver。
- Python 版本。
- PyTorch 版本。
- `torch.version.cuda`。
- `torch.cuda.get_device_capability()`。

### 阶段1：正确性 smoke test，30-60 分钟

先跑当前默认配置：

```bash
cd track1/official
CUDA_VISIBLE_DEVICES=0 \
MOE_SHARED_CHUNK_SIZE=131072 \
MOE_EXPERT_CHUNK_SIZE=131072 \
MOE_USE_CHECKPOINT=0 \
python correctness_check.py --solution solution.py --seq-len 8192
```

再跑低显存候选：

```bash
CUDA_VISIBLE_DEVICES=0 \
MOE_SHARED_CHUNK_SIZE=8192 \
MOE_EXPERT_CHUNK_SIZE=8192 \
MOE_USE_CHECKPOINT=1 \
python correctness_check.py --solution solution.py --seq-len 8192
```

任一候选 correctness 失败，直接淘汰，不进入 benchmark。

### 阶段2：128K 主搜索，半天内完成

候选列表：

```text
nocp_s32768_e32768
nocp_s65536_e65536
nocp_s131072_e131072
nocp_s196608_e196608
nocp_s262144_e262144

ckpt_s8192_e8192
ckpt_s16384_e16384
ckpt_s32768_e32768
ckpt_s65536_e65536
ckpt_s131072_e131072
```

每个配置：

```bash
CUDA_VISIBLE_DEVICES=0 \
MOE_SHARED_CHUNK_SIZE=<S> \
MOE_EXPERT_CHUNK_SIZE=<E> \
MOE_USE_CHECKPOINT=<0_or_1> \
python benchmark.py --solution solution.py \
  --seq-lens 131072 \
  --warmup 2 \
  --measure 3
```

淘汰规则：

- OOM 淘汰。
- correctness 未通过淘汰。
- 128K 平均时间比当前最快慢 3 倍以上，且显存不进入最低前 2，淘汰。
- 保留 Pareto front：不存在另一个配置同时显存更低且速度更快。

### 阶段3：Pareto 精测，半天内完成

对 Pareto 前 3-5 名跑：

```bash
python benchmark.py --solution solution.py \
  --seq-lens 8192,32768,65536,131072 \
  --warmup 5 \
  --measure 10
```

记录：

- `peak_mb`
- `avg_ms`
- `min_ms`
- `max_ms`
- 是否有异常波动
- correctness 是否重新通过

最终选择不应只看单次最小时间，优先看 `avg_ms` 和稳定性。

### 阶段4：长序列压力测试，可选

只对最终 2 个候选做：

```bash
python benchmark.py --solution solution.py \
  --seq-lens 196608,262144 \
  --warmup 1 \
  --measure 3
```

若失败但 128K 稳定，不应推翻主提交。除非官方明确测试 196K/262K，否则长序列只是鲁棒性信息。

### 阶段5：compile 分支，可选且限时

限时 2 小时。只尝试：

```text
compile=0
compile=max-autotune-no-cudagraphs
compile=default
```

不要先试整块 `forward`。更合理的是只 compile：

- `_shared_chunk`
- `_expert_chunk`

停止条件：

- 首次编译时间过长，影响当日主线实验。
- 显存增加超过 10%。
- correctness 有任何不稳定。
- 128K 平均速度收益低于 5%。

## 多卡并行调参方案

如果有 2-8 张 A800/H20：

- 每张卡一个独立 trial worker。
- 每个 worker 只绑定一张 GPU。
- 每个 trial 独立子进程启动，完成后写 JSONL/CSV。
- 共享同一个候选队列，但不要让多个 worker 跑同一个配置。

示例：

```bash
CUDA_VISIBLE_DEVICES=0 python run_trial.py --variant nocp_s131072_e131072
CUDA_VISIBLE_DEVICES=1 python run_trial.py --variant ckpt_s8192_e8192
CUDA_VISIBLE_DEVICES=2 python run_trial.py --variant nocp_s262144_e262144
```

如果使用 Optuna：

- sampler：`TPESampler(seed=2026)`
- pruner：`HyperbandPruner` 或 `SuccessiveHalvingPruner`
- storage：SQLite 或 MySQL
- trial 参数只包含 `shared_chunk`、`expert_chunk`、`checkpoint`、可选 `compile_mode`

但在截止日前更推荐当前的确定性候选队列，因为可解释、可复现、失败成本低。
