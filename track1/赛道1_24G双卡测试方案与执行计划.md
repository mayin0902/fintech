# 赛道1：24GB 双卡测试方案与执行计划

## 1. 目标

在比赛截止前，优先完成赛道1 `MoEBlockOptimized` 的有效提交：

- 正确性完全通过：前向输出、输入梯度、所有参数梯度。
- 在 24GB 卡上先完成小规模和中等规模测试，快速迭代优化思路。
- 有机会拿到 48GB/A800/官方环境后，再做 128K 长序列最终调参。

本方案不依赖多卡合并显存。比赛要求单卡执行，多张 24GB 只用于并行跑不同实验。

## 2. 环境策略

### 2.1 当前优先级

1. 先用 24GB 卡跑 correctness 和小规模 benchmark，不等待大显存机器。
2. 尽快拿到至少一张 48GB 或 A800 80GB，用来验证 `65536/131072`。
3. 若使用 Triton 或自定义 CUDA，最终必须回到官方环境：Python 3.12 + Torch 2.8.0 + CUDA 12.8。

### 2.2 24GB 双卡使用方式

- GPU0：跑 correctness、小尺寸回归、快速 benchmark。
- GPU1：跑长一点的 benchmark 或不同优化版本。
- 不做分布式初始化，不做模型并行，不把两张 24GB 当作一张 48GB。

建议命令形式：

```bash
CUDA_VISIBLE_DEVICES=0 python correctness_check.py --solution solution.py --seq-len 2048
CUDA_VISIBLE_DEVICES=1 python benchmark.py --solution solution.py --seq-lens 2048,8192 --warmup 1 --measure 3
```

## 3. 测试分层

### 3.1 CPU/小 GPU smoke

用途：检查参数名、load_state_dict、基础 forward/backward。

```bash
python correctness_check.py \
  --solution solution.py \
  --seq-len 128 \
  --hidden-size 256 \
  --intermediate-size 768 \
  --moe-intermediate-size 96 \
  --num-experts 16 \
  --top-k 4
```

### 3.2 24GB correctness

用途：确保默认配置下数学等价。

```bash
CUDA_VISIBLE_DEVICES=0 python correctness_check.py --solution solution.py --seq-len 2048
CUDA_VISIBLE_DEVICES=0 python correctness_check.py --solution solution.py --seq-len 8192
```

如 8192 OOM，先降低到 4096 排查正确性，再优化显存。

### 3.3 24GB benchmark

用途：观察显存趋势和速度变化，不作为最终排名依据。

```bash
CUDA_VISIBLE_DEVICES=1 python benchmark.py \
  --solution solution.py \
  --seq-lens 2048,8192,32768 \
  --warmup 1 \
  --measure 3
```

24GB 上 `65536` 和 `131072` 可能 OOM。OOM 不代表方案不可用，只说明需要更大显存做最终验证。

### 3.4 48GB/A800 最终验证

拿到大显存后重点跑：

```bash
python correctness_check.py --solution solution.py --seq-len 8192
python benchmark.py --solution solution.py --seq-lens 8192,32768,65536,131072 --warmup 3 --measure 10
```

最终至少记录：

- peak memory MB
- avg/min/max step time
- 是否通过 correctness
- 对比 baseline 的显存下降比例

## 4. 优化路线

### 4.1 第一版：稳定正确

目标：尽快让 `correctness_check.py` 通过。

实现原则：

- 保持参数名完全一致。
- 不改变 router、top-k、归一化、RMSNorm、shared expert、routed expert 数学定义。
- 避免 baseline 中 `one_hot(top_k_index, num_classes=128)` 形成的大型 expert mask。
- 按 expert 逐个处理命中的 token，使用 `torch.where(selected_experts == expert_id)` 或排序分组。

### 4.2 第二版：降低峰值显存

优先方向：

- 去掉巨大 one-hot expert mask。
- shared expert 使用 chunk 计算，避免一次性保存 `[tokens, 6144]` 的 gate/up/activation。
- routed expert 按 expert + token chunk 计算，控制中间激活生命周期。
- 对 shared expert 和 routed expert 使用 `torch.utils.checkpoint` 或自定义 autograd 做 recompute。

显存优先版本可以牺牲部分速度，因为评分权重显存 6、速度 4。

### 4.3 第三版：速度修正

在显存已经明显下降后优化速度：

- 减少 Python expert 循环中的空 expert 检查。
- 将 token 按 expert 排序，提升访问连续性。
- 对 top expert 的 token chunk 做批量矩阵乘。
- 时间足够再尝试 Triton grouped GEMM。

## 5. 风险控制

- 不在提交中依赖多卡。
- 不使用只能在本地 CUDA 13/Torch 2.9 编译的 `.so` 作为最终方案。
- 若没有官方镜像，优先提交纯 PyTorch/Triton JIT 方案，降低 ABI 风险。
- 每次优化后先跑 correctness，再跑 benchmark。
- 保留一个稳定正确版本作为 fallback。

## 6. 工作计划

### Day 1

- 建好 24GB 环境。
- 跑通附件原始脚本。
- 实现第一版正确方案。
- 通过小尺寸和默认 `seq_len=2048` correctness。

### Day 2

- 去掉 one-hot mask。
- 加 shared expert chunk。
- 跑 `2048,8192,32768` benchmark。
- 记录每个版本显存和速度。

### Day 3

- 加 routed expert chunk/recompute。
- 尝试 48GB/A800 跑 `65536,131072`。
- 如果速度太慢，调 chunk size。

### Day 4

- 固化最稳版本。
- 准备 `solution.py`、报告 PDF。
- 在最大可用显存机器上做最终复测。

## 7. 推荐提交策略

优先提交“正确性稳 + 显存明显降低”的版本，而不是追求复杂 CUDA kernel。

若时间不足：

1. 保证 correctness 全通过。
2. 保证 8K 和 128K 至少不 OOM或显著低于 baseline。
3. 接受一定速度损失。

若时间充足：

1. 在稳定 PyTorch 版本基础上增加 Triton 优化。
2. 保留环境开关，Triton 失败时自动 fallback 到 PyTorch。
