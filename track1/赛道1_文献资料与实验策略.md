# 赛道1：文献资料与实验策略

## 1. 结论

优先参加赛道1，并采用“纯 PyTorch + chunk + checkpoint/recompute”的稳健路线。

理由：

- 赛道1只要求优化一个 MoE Block，不需要下载大模型权重。
- 正确性是硬门槛，复杂 CUDA/Triton kernel 容易在 backward 或参数梯度上出问题。
- 显存评分权重为 6、速度评分权重为 4。先降低峰值显存，再修速度，是更稳的竞赛策略。
- 24GB 双卡可以并行跑不同实验，但不能合并显存，最终实现必须单卡可运行。

## 2. 关键资料与启发

### 2.1 Activation Checkpointing

资料：

- PyTorch `torch.utils.checkpoint` 文档：<https://docs.pytorch.org/docs/stable/checkpoint>
- PyTorch checkpointing 技术博客：<https://pytorch.org/blog/activation-checkpointing-techniques/>
- Chen et al., *Training Deep Nets with Sublinear Memory Cost*：<https://arxiv.org/abs/1604.06174>

启发：

- checkpoint/recompute 是标准的“用额外计算换显存”方法。
- 对赛题而言，shared expert 和 routed expert 的 MLP 中间激活是优先 checkpoint 的对象。
- 建议使用 `use_reentrant=False`，并在无随机操作时设置 `preserve_rng_state=False`，减少额外开销。

### 2.2 MoE Expert 分组与稀疏计算

资料：

- MegaBlocks: *Efficient Sparse Training with Mixture-of-Experts*：<https://arxiv.org/abs/2211.15841>
- Tutel: *Adaptive Mixture-of-Experts at Scale*：<https://arxiv.org/abs/2206.03382>
- Switch Transformers：<https://arxiv.org/abs/2101.03961>
- GShard：<https://arxiv.org/abs/2006.16668>

启发：

- MoE 的关键不是参数显存，而是 token routing 后的中间激活、padding、分组和 scatter/gather。
- baseline 中 `one_hot(top_k_index, num_classes=128)` 在长序列上会产生很大的临时张量，应优先去掉。
- MegaBlocks/Tutel 的共同方向是按 expert 分组、减少 padding 和无效计算；赛题单卡版本也应沿这个方向做。

### 2.3 Triton / Grouped GEMM

资料：

- Triton grouped GEMM 教程：<https://triton-lang.org/main/getting-started/tutorials/08-grouped-gemm.html>
- Triton matmul 教程：<https://triton-lang.org/main/getting-started/tutorials/03-matrix-multiplication.html>

启发：

- Triton grouped GEMM 适合作为后期加速项。
- 但赛题需要 forward、input grad、所有参数 grad 全部等价，直接写自定义 kernel 的风险较高。
- 建议先做 PyTorch 正确版本，再考虑用 Triton 替换局部瓶颈。

### 2.4 torch.compile

资料：

- PyTorch `torch.compile` 文档：<https://docs.pytorch.org/docs/stable/generated/torch.compile.html>

启发：

- `torch.compile` 对动态 expert loop 未必稳定。
- `mode="reduce-overhead"` 可能引入 CUDA graph 和额外显存，不一定适合显存优化目标。
- 可以只尝试 compile 小函数，如 shared expert chunk 或单 expert MLP；不要把它作为第一优先级。

## 3. 推荐实现路线

### V0：环境与 baseline wrapper

目的：

- 确认 24GB 机器环境可运行。
- 确认 `correctness_check.py` 和 `benchmark.py` 没有路径或依赖问题。

做法：

- 先跑官方 `solution.py`，确认会触发 `NotImplementedError`。
- 写一个临时 `solution_baseline.py`，直接复用 baseline 逻辑，只用于校验脚本流程。

### V1：去掉 one-hot expert mask

baseline 风险点：

```python
expert_mask = F.one_hot(top_k_index, num_classes=self.num_experts)
expert_mask = expert_mask.permute(2, 1, 0)
```

优化方向：

- 不构造 `[tokens, top_k, num_experts]` 的 one-hot。
- 对每个 expert 使用布尔 mask 或 `torch.where(selected_experts == expert_id)` 找命中 token。
- 逐 expert 处理并 `index_add_` 回写。

预期：

- 显著降低长序列临时张量。
- 正确性风险低。
- Python loop 会慢，但可接受作为 V1。

### V2：shared expert chunk + checkpoint

shared expert 的主要显存来自：

- `gate_proj(x)` -> `[tokens, 6144]`
- `up_proj(x)` -> `[tokens, 6144]`
- `silu(gate) * up`

优化方向：

- 按 token chunk 计算 shared expert。
- 对 chunk 内 shared MLP 使用 checkpoint/recompute。

建议 chunk：

- 24GB：`1024, 2048, 4096`
- 48GB：`4096, 8192`
- 80GB：`8192, 16384`

### V3：routed expert chunk + checkpoint

优化方向：

- 每个 expert 内部再按 token chunk 计算。
- 不展开 `[tokens * top_k, hidden]`。
- 不保存所有 expert 的中间激活。
- chunk 内做 `gate/up/down`，再乘 top-k weight 并 `index_add_`。

关键点：

- 保持 top-k 权重归一化逻辑完全一致。
- 保持 bf16/float32 softmax 行为一致。
- 每次改动后先跑 correctness。

### V4：速度修正

在正确性和显存稳定后再做：

- 预先统计每个 expert 的命中 token。
- 将 `(token_idx, top_k_pos, expert_id)` 排序，减少重复 `where`。
- 对高频 expert 使用更大 chunk。
- 低频 expert 可合并或走简单路径。
- 时间充足再尝试 Triton grouped GEMM。

## 4. 硬件分工

| 显存 | 能做什么 | 不建议做什么 |
|---|---|---|
| 24GB 单卡 | correctness、小尺寸 smoke、`2048/8192/32768` 趋势测试 | 不用它判断 128K 最终排名 |
| 24GB 双卡 | 并行跑不同实验：一张 correctness，一张 benchmark | 不要用多卡合并显存，比赛不允许 |
| 48GB | 跑 `32768/65536`，尝试优化版 `131072`，调 chunk size | 仍不要作为最终 H20 性能依据 |
| 80GB A800 | 主力长序列验证，跑 `8192/32768/65536/131072`，接近最终策略 | 若有 custom CUDA，仍需官方 CUDA 12.8/Torch 2.8 复测 |

## 5. 24GB 双卡实验命令

### 正确性

```bash
cd track1/official

CUDA_VISIBLE_DEVICES=0 python correctness_check.py \
  --solution solution.py \
  --seq-len 128 \
  --hidden-size 256 \
  --intermediate-size 768 \
  --moe-intermediate-size 96 \
  --num-experts 16 \
  --top-k 4

CUDA_VISIBLE_DEVICES=0 python correctness_check.py \
  --solution solution.py \
  --seq-len 2048
```

### 小规模 benchmark

```bash
CUDA_VISIBLE_DEVICES=1 python benchmark.py \
  --solution solution.py \
  --seq-lens 2048,8192,32768 \
  --warmup 1 \
  --measure 3
```

## 8. 实验效率建议

- 每个 seq_len 单独起进程，避免 OOM 后显存碎片影响下一轮。
- 每次只改一个变量：shared chunk、expert chunk、checkpoint 开关、排序策略。
- 先跑 tiny correctness，再跑默认 `2048` correctness，最后跑 benchmark。
- 24GB 上只看趋势，不看最终绝对值。
- 保留一个“正确但慢”的 fallback 版本。

## 9. 风险排序

从低风险到高风险：

1. 去掉 one-hot mask。
2. shared expert chunk。
3. routed expert chunk。
4. checkpoint/recompute。
5. expert 排序和分组。
6. torch.compile 局部函数。
7. Triton grouped GEMM。
8. 自定义 CUDA extension。

当前时间紧，建议做到 1-5，最多尝试 6；7-8 只在正确版本稳定后作为加分项。

## 10. 最终提交原则

- correctness 必须全通过。
- 优先提交显存低且稳定的版本。
- 速度可以适当牺牲，但不能慢到 benchmark 无法完成。
- 如使用 Triton，必须提供 PyTorch fallback。
- 如使用自定义 CUDA `.so`，必须在官方 CUDA 12.8 + Torch 2.8.0 环境复测。
